# cloud-cypher

[Опубликованные результаты и воспроизведение проверок](reports/README.md)

Браузерный клиент зашифрованного файлового хранилища и отдельный инструмент для проверки доставленного кода. Сервер хранит зашифрованные файлы, зашифрованные имена и упаковки ключей; расшифрование выполняется на устройстве пользователя.

**Статус: прототип для проверки архитектуры и интеграции, не проверенный production-продукт.** Криптографический формат, вход и восстановление требуют независимого аудита. Браузерная версия не защищает от владельца сервера, который подменяет выдаваемый JavaScript: он может перехватить пароль, ключи или файлы. Инструмент проверки сравнивает полученные байты с независимым эталоном, но не блокирует исполнение кода до проверки.

## Устройство

```text
Пароль → OPAQUE exportKey → ключ упаковки ──┐
                                         ├→ ключ хранилища → ключ каждого файла
Passkey с PRF → отдельный ключ упаковки ──┘

Сервер: зашифрованные упаковки, метаданные и файлы
Браузер: проверка аутентичности, расшифрование и просмотр
```

Для парольного входа используется зафиксированная библиотека OPAQUE. Из клиентского `exportKey` через HKDF-SHA-256 получается ключ упаковки. Известный серверу OPAQUE `sessionKey` для защиты файлов не используется. Пароль не отправляется серверу в открытом виде штатным клиентом. Интеграция Nimbus завершает парольный вход вторым фактором: email-кодом либо кодом из настроенного TOTP-приложения. Вход с passkey подтверждается WebAuthn user verification и не требует этого OTP-шага.

Вход по passkey и восстановление забытого пароля реализованы как второй путь к тому же ключу хранилища. Для этого нужна поддержка WebAuthn PRF: обычной подписи passkey недостаточно для расшифрования файлов. Перед загрузкой Nimbus требует активированный passkey с подтверждённым состоянием резервирования. Утверждение аутентификатора о резервировании не доказывает, что конкретный пользователь сможет восстановить его после потери всех устройств. Реальная синхронизация и восстановление у провайдеров на физических устройствах требуют отдельной проверки.

**TOTP — отдельный фактор проверки входа, а не ключ файлов.** Стандартный сервер проверки TOTP знает тот же seed, что и приложение кодов. Поэтому TOTP не может сам по себе восстановить забытый ключ и одновременно скрыть его от администратора такого сервера. Реализованная замена email-кодов на TOTP не меняет это ограничение: для расшифрования по-прежнему нужен пароль или подходящий passkey.

Нет пользовательских recovery-кодов или привязки ключей к Telegram. Внутренний префикс `cc1-` в `crypto.js` обозначает техническую сериализацию 256-битного секрета между модулями и не является дополнительным секретом для ручного ввода.

## Файлы и ключи

- Случайный 256-битный ключ хранилища упакован с помощью AES-256-GCM.
- У каждого файла новый случайный 256-битный ключ и 96-битный nonce. Имена, MIME type, размер и ключ файла находятся внутри отдельно зашифрованных метаданных.
- AAD привязывает контейнеры к версии формата и UUID хранилища/файла. Проверка тега выполняется до скачивания или превью.
- Ключи используются в памяти открытой страницы. В localStorage сохраняются только тема и вид списка; пароль и ключи туда не записываются.
- Смена пароля переупаковывает существующий ключ хранилища. Файлы сохраняются. Восстановление пароля с помощью подходящего passkey делает то же самое; простая смена пароля сервером без клиентского ключа не открывает старые файлы.
- Потеря всех способов открыть ключ отличается от потери устройства. Если не осталось ни пароля, ни восстанавливаемого подходящего passkey, обычная серверная проверка личности не даёт ключ расшифрования. Сброс потерянного passkey через email требует явно подтвердить удаление всех файлов, после чего можно создать пустое хранилище с новым паролем и passkey.

Версия 1 обрабатывает целый файл в памяти, максимум 50 МиБ открытых данных. Загрузка не возобновляется по частям. Каждый файл занимает на сервере на 16 байт больше открытого размера; загрузка также ограничена свободной квотой. В интеграции Nimbus перед первой загрузкой нужно активировать дополнительную упаковку ключа под passkey. Открытый просмотр поддерживает только PNG, JPEG, GIF и WebP. Общий доступ к зашифрованным файлам не реализован.

## Использование и интеграция

Каталог `web/` содержит готовые файлы сайта. Собственный клиент не требует сборки или внешнего CDN. Зависимость `web/vendor/opaque.js` включает заранее скомпилированный WASM из зафиксированного npm-пакета; это исполняемая зависимость, которую тоже нужно проверять.

Для рабочих сценариев нужен сервер: сессии, CSRF, OPAQUE, WebAuthn, приватные объекты, квоты и жизненный цикл ключей. Реализация Nimbus находится в [cloud-nimbus-e2ee](https://github.com/wywywywycloud/cloud-nimbus-e2ee). Одна статическая раздача `web/` не заменяет этот backend. Приложение использует тот же origin для API, а в удалённом окружении требует HTTPS.

Основные модули:

| Файл | Назначение |
| --- | --- |
| `web/crypto.js` | Формат AES-GCM, проверка контейнеров, упаковка ключа |
| `web/http.js` | Ограничение размера и разбор ответов API входа |
| `web/account.js` | Парольная регистрация и вход OPAQUE |
| `web/passkeys.js` | Прототип WebAuthn PRF, отдельная упаковка ключа и вход по passkey |
| `web/app.js` | Файлы, скачивание, просмотр, состояние открытого хранилища |
| `web/verify.html` | Объяснение границ защиты и проверки до входа |
| `tools/verify.py` | Независимое сравнение HTTP-ответов или предоставленного HAR |
| `tools/vendor_opaque.py` | Проверка происхождения и восстановление зафиксированных байтов OPAQUE |

## Проверки

Нужны Node.js 22+ с Web Crypto и Python 3.9+. Для этих команд сторонние Python-пакеты и `npm install` не требуются:

```sh
node --test tests/*.test.mjs
python3 -m unittest discover -s tests -p 'test_*.py' -v
python3 tools/vendor_opaque.py --check
```

Первые проверки охватывают порчу данных, неправильные ключи, подмену UUID, строгие форматы, пределы размера, переупаковку ключей и подмены наблюдаемых файлов сайта. Отдельные тесты проверяют, что запрос WebAuthn не включает PRF-секрет, а ответы API входа ограничены по фактическому размеру. Эти проверки не подтверждают корректность всего приложения или отсутствие уязвимостей браузера и провайдера passkey. Playwright указан только как зависимость для проверки интерфейса и не поставляется пользователю.

Интеграционные браузерные проверки Nimbus прошли парольный вход OPAQUE в новом контексте браузера, подключение и вход по виртуальному passkey с PRF, восстановление пароля с сохранением файлов, явный сброс с удалением файлов и вход с TOTP. Виртуальный аутентификатор проверяет взаимодействие приложения с браузером; он не проверяет синхронизацию реального менеджера паролей и восстановление его аккаунта после потери устройства.

Для публичной проверки выберите независимо полученную и проверенную локальную копию релиза:

```sh
python3 tools/verify.py manifest --root web --output release-manifest.json --headers-policy headers-policy.json
python3 tools/verify.py verify-url --manifest release-manifest.json --base-url http://127.0.0.1:8017/vault/ --report url-report.json
```

HTTP здесь допустим только для локального стенда. Для удалённого сервиса используйте HTTPS. Эталон нельзя одновременно скачивать с проверяемого сайта и считать независимым. `verify-url` проверяет новые ответы наблюдателю; `verify-har` сравнивает тела из конкретного предоставленного журнала. Сервер может выдавать другой код другим пользователям или в другое время. Подробные инструкции и ограничения находятся в [VERIFICATION.md](docs/VERIFICATION.md).
