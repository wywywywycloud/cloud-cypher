# Проверка доставленного веб-клиента

Публичные исходники позволяют проверять программу. Чтобы проверить связь между
ними и сайтом, нужно отдельно сравнить опубликованную версию с фактически
полученными байтами. `tools/verify.py` выполняет это сравнение вне сайта, используя
только стандартную библиотеку Python 3.9+.

В этой версии `web/` содержит готовые исходные HTML, JavaScript и CSS. Наш клиент
не требует минификации или транспиляции: публикуемые байты должны совпадать с
файлами `web/`. Единственная поставляемая сторонняя исполняемая зависимость —
`vendor/opaque.js`: зафиксированный npm-артефакт OPAQUE со встроенным скомпилированным
WebAssembly. Его происхождение и сверка описаны в [SECURITY.md](SECURITY.md).
Сравнение поставленных байтов не доказывает безопасность исходников, библиотеки
или соответствие встроенного WASM исходному Rust-коду.

## Сначала получить независимый эталон

Получите исходники выбранного релиза из независимо проверенного источника и
проверьте их. Эталон — именно эта локальная копия. Не скачивайте одновременно
клиент и «доверенный манифест» с проверяемого сервера: владелец может заменить оба.
Хеш коммита или манифеста нужно сверять по отдельному доверенному каналу. Этот
инструмент не проверяет подписи релизов, не определяет надёжность источника и не
выбирает доверенный релиз автоматически.

Из корня отдельного проекта `cloud-cypher`:

```sh
python3 tools/verify.py manifest --root web --output release-manifest.json --headers-policy tools/nimbus-headers.json
```

Манифест содержит относительные пути, SHA-256 и длины всех файлов `web/`, кроме
самого файла вывода, если он размещён внутри этого каталога. Никакие другие файлы
не исключаются автоматически. Пути отсортированы, временных меток нет: одинаковые
исходники и политика дают одинаковый манифест. Ссылки на файлы и каталоги не
допускаются. Один файл ограничен 32 MiB.

`tools/nimbus-headers.json` — локальная ожидаемая политика Nimbus. Она не
запрашивается у проверяемого сервера. Если приложение развёртывается с другой
политикой, её нужно осознанно проверить и передать отдельным локальным JSON-файлом.
Поле манифеста `response_headers` требует точного совпадения значений после удаления
начальных и конечных пробелов; отсутствие или повтор требуемого заголовка считается
несоответствием. Проверяются только объявленные заголовки. Без `--headers-policy`
заголовки не проверяются, и отчёт явно содержит
`"security_header_policy_checked": false`.

## Два разных режима наблюдения

### Новые запросы независимого наблюдателя

```sh
python3 tools/verify.py verify-url --manifest release-manifest.json --base-url http://127.0.0.1:8017/vault/ --report url-report.json
```

Команда делает новые HTTP-запросы без пользовательской сессии к каждому файлу
манифеста и к `/vault/`, сравнивая последний с `index.html`. Редиректы запрещены;
код не уходит вслед за перенаправлением на другой адрес. Нужен ответ 200 с телом;
отсутствие файла, сетевая ошибка и неподдерживаемое сжатие ответа не дают успеха.
Для удалённого сервиса используйте HTTPS; HTTP в примере предназначен для localhost.

**Это проверка новых ответов серверa наблюдателю. Она не показывает, что сервер
ранее отправил конкретному пользователю.** Сервер способен различать запросы,
IP-адреса, сессии и время. Команда также не запускает JavaScript и не обнаруживает
все потенциальные динамические загрузки. Хеш HTML обнаружит добавленный в него
скрипт, но инструмент не является сканером поведения программы.

### Ответы из конкретного предоставленного HAR

HAR — экспорт сетевого журнала браузера. Чтобы получить полезный журнал:

1. Завершите вход в аккаунт, затем откройте инструменты разработчика на `/vault/`.
2. Откройте вкладку Network, очистите журнал, включите сохранение запросов при
   переходах и отключение сетевого кэша, пока инструменты открыты.
3. Перезагрузите `/vault/` и выполните проверяемый сценарий. Экспортируйте HAR
   **с содержимым ответов**, а не только адресами и заголовками.
4. Сохраните его локально и запустите сравнение с независимым эталоном:

```sh
python3 tools/verify.py verify-har --manifest release-manifest.json --har capture.har --base-url http://127.0.0.1:8017/vault/ --report har-report.json
```

Не публикуйте исходный HAR: он может содержать cookies, параметры авторизации,
имена файлов и тела ответов. Проверяющий инструмент не передаёт HAR по сети и не
включает тела, URL-параметры, cookies или значения заголовков в отчёт. В отчёте
остаются известные пути манифеста, хеши, статусы и коды обнаруженных проблем;
посторонние адреса обозначаются общим кодом без их содержимого.

Для обычного экрана по умолчанию нужны `index.html`, `app.js`, `crypto.js`,
`http.js`, `account.js`, `passkeys.js`, `vendor/opaque.js` и `style.css` — если они
присутствовали при создании манифеста. `index.html` обязателен
всегда. `verify.html` присутствует в манифесте, но не обязан загружаться в каждой
сессии. Каждый наблюдавшийся файл всё равно проверяется. Непросмотренные файлы
явно перечислены в `unobserved_paths`; совпадение основной страницы не означает,
что проверены все остальные страницы релиза.

При необходимости задайте охват явно повторяемым `--require-path`; список заменяет
обычный набор, поэтому перечислите все необходимые файлы, включая `index.html`:

```sh
python3 tools/verify.py verify-har --manifest release-manifest.json --har capture.har --base-url http://127.0.0.1:8017/vault/ --require-path index.html --require-path app.js --require-path crypto.js --require-path http.js --require-path account.js --require-path passkeys.js --require-path vendor/opaque.js --require-path style.css --require-path verify.html --report full-har-report.json
```

Правила обработки HAR:

- `/vault/` соответствует `index.html`; query-параметры не входят в отчёт, но тело
  каждого ответа с такими параметрами проверяется отдельно.
- Отсутствующее тело, ответ 304, ошибка запроса или отсутствие обязательного файла
  означают неполную проверку. Сведения о кэше не подменяют отсутствующие байты.
- Base64 декодируется строго. Текст без `encoding` восстанавливается как UTF-8;
  для произвольных бинарных файлов нужен экспорт тела как Base64. Сопоставляются
  экспортированные байты после транспортного декодирования, не сжатый HTTP-поток.
- Повторные ответы проверяются все. Успешный ответ не отменяет другой, изменённый
  или неполный ответ того же файла.
- Неизвестный ресурс внутри `/vault/` считается несоответствием. Вне этого пути
  отмечаются неизвестные HTML/JS/WASM/CSS и worker-ресурсы, обнаруженные по типу,
  MIME или расширению. Если журнал включает страницу входа, другую вкладку или
  чужие документы, они тоже могут вызвать отказ: используйте журнал только
  проверяемого сценария, а не удаляйте подозрительные запросы ради успеха.
- Source maps и дополнительные «исходники» DevTools не заменяют тела реально
  доставленных ответов. Сопоставляется `response.content.text`.

## Как читать результат

| Код завершения | `status` | Значение |
| --- | --- | --- |
| `0` | `verified_scope` | Байты и объявленные заголовки совпали в описанном охвате |
| `1` | `mismatch` | Найдено хотя бы одно несоответствие, включая посторонний код |
| `2` | `incomplete` | Неполные, ошибочные или недоступные входные данные/ответы |

При одновременно найденных несоответствиях и пробелах охвата код будет `1`, а
отчёт сохранит оба вида проблем. Ни одна неполная проверка не получает код `0`.

`verified_scope` **не означает «сайт безопасен»**. HAR можно отредактировать;
инструмент не удостоверяет его происхождение. Даже настоящий HAR не гарантирует,
что журнал содержит каждое исполнение: ранее загруженные service workers, кэши,
другие контексты, генерируемый код и особенности экспорта требуют отдельного
анализа. Штатный клиент Nimbus запрещает workers своей объявленной CSP, но это
не превращает HAR в доказательство полного состояния браузера.

Проверка выполняется после получения ответов. Она не блокирует исполнение
вредоносного кода и не возвращает уже раскрытые секреты. До проверки на незнакомом
сайте не вводите рабочий пароль, не используйте секреты passkey и не выбирайте чувствительные файлы; для
пробного сценария используйте отдельное тестовое хранилище с несекретными данными.

Наконец, совпадение с опубликованной программой не доказывает её корректность:
в опубликованном исходном коде тоже может быть ошибка или намеренная утечка.
Нужны независимая проверка кода и устройства, а для автоматического предотвращения
подмены до исполнения — отдельная доверенная точка проверки. Серверный runtime,
сохранение дополнительных серверных копий, выдача другим пользователям и будущие
релизы этим инструментом не проверяются.

## Проверка самого инструмента

```sh
python3 -m unittest discover -s tests -p test_verify.py -v
```

Тесты поднимают локальный HTTP-сервер с намеренными подменами и используют
синтетические HAR: проверяются подменённые файлы, редиректы, пропущенные и
кэшированные ответы, конфликтующие дубликаты, посторонние скрипты, подмена
source maps, неправильные заголовки, Base64, пути и JSON-структура.
