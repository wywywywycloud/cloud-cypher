# cloud-cypher: формат зашифрованного хранилища, версия 1

Этот документ описывает формат `web/crypto.js`. Учётные записи, OPAQUE, passkey и серверная авторизация являются отдельными слоями. Файлы не зависят от способа входа: клиент получает ключ хранилища, а сервер сохраняет зашифрованные объекты.

Собственный криптографический примитив здесь не реализован. Все операции AES и генерация случайных чисел выполняются Web Crypto платформы. Формат нуждается в независимом аудите перед использованием для критичных данных; наличие тестов не заменяет аудит.

## Представление

- Версия всех контейнеров — целое число `1`. Другие версии отклоняются.
- Идентификаторы хранилища и файла — канонические UUIDv4 в нижнем регистре, с дефисами и RFC variant bits (`8`, `9`, `a` или `b` в начале четвёртой группы).
- Двоичные поля JSON используют канонический base64url без padding. Пробелы, `=`, стандартные `+` и `/`, неоднозначные завершающие биты и неверная длина отклоняются.
- Строки AAD кодируются UTF-8, без BOM и завершающего NUL.
- AES-GCM использует 256-битный ключ, случайный 96-битный nonce и 128-битный тег. Двоичный шифротекст представлен как `ciphertext || tag`, в соответствии с Web Crypto.
- Метаданные шифруются после кодирования JSON в UTF-8. Их зашифрованный контейнер не может превышать 8192 байта. JSON envelope содержит ровно `v`, `iv` и `ct`.

## 1. Ключ хранилища

Клиент генерирует случайный ключ хранилища `VK` размером 32 байта. Он не получается из идентификатора аккаунта, email, Telegram ID или других публичных данных.

Внешний механизм входа предоставляет отдельный 32-байтовый секрет упаковки `WK`. Внутренний интерфейс `crypto.js` принимает его как строку `cc1-` и 43 символа base64url. Это техническое представление ключа между клиентскими модулями, **не отдельный код, который пользователь должен сохранять или вводить**. Имена низкоуровневых функций `generateRecoveryCode` и `parseRecoveryCode` сохранены в модуле, но их результаты не выводятся пользователю и не отправляются серверу.

Для парольного входа `account.js` получает `WK` из клиентского `exportKey` протокола OPAQUE:

```text
WK = HKDF-SHA-256(
    IKM = OPAQUE exportKey,
    salt = UTF8("cloud-cypher:opaque-wrap:v1"),
    info = UTF8(canonical_username),
    length = 32 bytes
)
```

`exportKey` нельзя подменять `sessionKey`: ключ сессии OPAQUE известен серверу.

Для passkey модуль `passkeys.js` использует отдельную упаковку того же `VK`. Клиент самостоятельно задаёт постоянный вход WebAuthn PRF, а 32-байтовый результат расширения обрабатывает через HKDF:

```text
PRF_input = SHA-256(UTF8("cloud-cypher:passkey-prf:v1"))
WK_passkey = HKDF-SHA-256(
    IKM = WebAuthn PRF results.first,
    salt = UTF8("cloud-cypher:passkey-wrap:v1"),
    info = UTF8(credential.id),
    length = 32 bytes
)
```

Парольная и passkey-упаковки используют один формат AES-GCM и AAD хранилища ниже, но разные ключи упаковки. Сервер хранит только дополнительную упаковку, публичный ключ WebAuthn и данные проверки подписи. PRF-результат не включается в запрос: клиент сериализует только явный список публичных полей credential и не вызывает общий `credential.toJSON()`. Код требует текущий hostname как RP ID, user verification и для регистрации resident key. Серверная активация и политика резервирования проверяются отдельно интеграцией Nimbus; поддержка PRF конкретным браузером и менеджером является обязательным условием этого способа расшифрования.

Ключ `VK` шифруется под `WK`:

```text
AAD = UTF8("cloud-cypher:vault:v1:" + vault_id)
wrapped_key.ct = AES-256-GCM(WK, random_nonce_12_bytes, VK, AAD)
```

Серверная запись:

```json
{
  "id": "2aa03e24-471c-4e59-8e32-71eeb48e0a2c",
  "version": 1,
  "wrapped_key": {"v": 1, "iv": "<base64url, 12 bytes>", "ct": "<base64url, 48 bytes>"}
}
```

JSON объекта хранилища содержит ровно эти три поля. Незашифрованный `VK` не хранится в БД и не передаётся серверу. В браузере он импортируется как non-extractable `CryptoKey` с разрешениями `encrypt` и `decrypt`.

## 2. Содержимое файла

Каждая операция шифрования файла создаёт новый случайный `FK` размером 32 байта и новый случайный nonce `FIV` размером 12 байт. Даже повторная запись того же содержимого под тем же идентификатором не использует прежнюю пару ключа и nonce.

```text
AAD = UTF8("cloud-cypher:file:v1:" + vault_id + ":" + file_id)
file_ciphertext = AES-256-GCM(FK, FIV, plaintext_bytes, AAD)
```

Файл обрабатывается целиком. Максимальный открытый размер одного файла — `50 * 1024 * 1024` байт; пустой файл разрешён. Размер шифротекста всегда равен открытому размеру плюс 16 байт. Это **не** потоковый формат: у него нет частей, продолжения прерванной загрузки или независимой проверки фрагментов.

Фактическая возможность загрузки ограничена также свободной серверной квотой. Например, при квоте ровно 50 МиБ нельзя загрузить открытый файл ровно 50 МиБ: нужен ещё 16-байтовый тег. При выборе нескольких файлов клиент учитывает тег каждого файла до начала отправки; сервер повторно и атомарно проверяет квоту.

## 3. Метаданные и ключ файла

Открытые метаданные имеют ровно пять полей:

```json
{
  "name": "Документ.txt",
  "type": "text/plain",
  "size": 123,
  "key": "<base64url FK, 32 bytes>",
  "iv": "<base64url FIV, 12 bytes>"
}
```

Валидация после успешной аутентификации:

- `name` — непустая строка не длиннее 1024 байт UTF-8; запрещены `/`, `\`, NUL, управляющие ASCII-символы, отдельные `.` и `..`;
- `type` — MIME type в нижнем регистре, не более 127 символов, без параметров и управляющих символов; неизвестный тип при создании заменяется на `application/octet-stream`;
- `size` — безопасное целое число от 0 до 50 МиБ;
- `key` — ровно 32 байта, `iv` — ровно 12 байт;
- `size + 16` должен совпадать с `ciphertext_bytes` записи файла.

Метаданные шифруются ключом хранилища с ещё одним случайным nonce:

```text
AAD = UTF8("cloud-cypher:metadata:v1:" + vault_id + ":" + file_id)
metadata.ct = AES-256-GCM(VK, random_nonce_12_bytes, UTF8(JSON(metadata)), AAD)
```

Сервер получает, например:

```json
{
  "id": "f51581f6-5ef1-4cb0-bc43-29e7f9b915d5",
  "vault_id": "2aa03e24-471c-4e59-8e32-71eeb48e0a2c",
  "metadata": {"v": 1, "iv": "<base64url, 12 bytes>", "ct": "<base64url>"},
  "ciphertext_bytes": 139,
  "created_at": "2026-09-26T12:00:00Z"
}
```

Сам шифротекст файла передаётся отдельным бинарным полем multipart. Имя multipart-файла формируется из UUID и `.bin`; исходное имя не должно попадать в заголовки запросов или серверные журналы.

## 4. Открытие файла

Клиент проверяет UUID, принадлежность текущему хранилищу, версию, длины и кодировку. Затем аутентифицирует и расшифровывает метаданные, проверяет их структуру и ожидаемый размер. Полученный файл обязан иметь ровно `ciphertext_bytes` байт. Только после успешной AES-GCM аутентификации содержимого клиент создаёт скачивание или превью.

Неверный ключ, изменение тега или содержимого, перестановка байтов, усечение, дописывание и перенос шифротекста под другой UUID завершаются ошибкой. Непроверенные открытые байты не выдаются вызывающему коду. Шифрование метаданных и файла раздельно привязано к паре `vault_id/file_id`.

Имена и другие серверные данные вставляются в DOM через `textContent`, а не HTML. Скачивания используют Blob с `application/octet-stream`. Встроенный просмотр ограничен PNG, JPEG, GIF и WebP: проверяются и аутентифицированный MIME type, и сигнатура расшифрованного файла. SVG, HTML и PDF не открываются inline. Object URL отзываются после использования, при закрытии превью и при блокировке хранилища.

## 5. Смена пароля

`rewrapVault(vault, oldWrappingSecret, newWrappingSecret)` открывает существующий `VK`, создаёт новый случайный nonce и возвращает новую упаковку того же ключа. Файлы и их ключи не изменяются. Замена парольной регистрации и упаковки на сервере должна выполняться атомарно, иначе пароль и ключ хранилища могут перестать соответствовать друг другу.

Смена упаковки не аннулирует ранее скопированные старые упаковки и старые ключи. Если злоумышленник знает прежний секрет и сохранил прежнюю запись, он может расшифровать старый `VK`. Для смены самого `VK` нужен отдельный процесс миграции данных; этот формат не выдаёт простую смену пароля за такую миграцию.

## 6. Границы защиты

Сервер видит аккаунт-владелец, UUID, зашифрованные размеры, число файлов, временные отметки и операции доступа. Имя, MIME type и содержимое файла скрыты только пока сервер не получил клиентские ключи.

**Браузерный клиент скачивается с сервера.** Владелец сервера, который заменит JavaScript, может перехватить введённый пароль, ключи или открытые файлы. Открытый код, хеши, CSP, Web Crypto и OPAQUE сами по себе не обеспечивают автоматическую защиту от такой подмены. Проверка исходников полезна только в рамках явно выбранной модели доверия и не делает произвольную загруженную страницу доверенной.

AES-GCM не обеспечивает доступность данных: сервер может удалить объекты, отказаться отвечать или вернуть старую, ранее действительную версию файла. В версии 1 нет внешнего журнала для обнаружения отката всего хранилища. Нельзя гарантировать удаление уже скачанных копий, локальных копий ключей или серверных резервных копий одной операцией в UI.

Ключи и открытое содержимое не записываются клиентом в localStorage, sessionStorage или IndexedDB. Сохраняются только несекретные настройки темы и вида. При выходе, блокировке и `pagehide` клиент удаляет доступные ссылки на ключи, очищает поля пароля, отзывает Object URL и прерывает сетевые операции. Временные изменяемые буферы затираются, где это возможно. JavaScript, Web Crypto и сборщик мусора **не дают гарантии физического стирания всех копий из оперативной памяти**.

## 7. Проверки

Запуск из корня `cloud-cypher`:

```sh
node --test tests/crypto.test.mjs
```

Тесты используют нативную Web Crypto реализацию Node.js. Проверяются неправильные секреты, порча тегов и содержимого, привязка AAD к обоим UUID, усечение и перестановка, строгие длины и версии, неизвестные поля, небезопасные имена, размеры, пустые/Unicode-файлы, файл более 2 МиБ и смена упаковки без изменения ключа данных. Отдельные проверки интеграции нужны для аккаунтов, passkey, серверной квоты, CSRF, межпользовательского доступа и UI.

## 8. Папки (2026-09-28)

Имена папок зашифрованы AES-256-GCM ключом vault с новым случайным 96-bit IV и
AAD `cloud-cypher:folder:v1:<vault UUID>:<folder UUID>`. Plaintext — UTF-8 JSON `{name}`;
имя имеет те же ограничения, что имя файла. Конверт `{v:1, iv, ct}`.
Связь parent_id, starred, trashed_at и тип folder видны серверу и не защищены этим AAD.
Это расширение не меняет ciphertext/metadata прежних файлов. Имена расшифровываются
только в памяти браузера. Перемещение и корзина не требуют перешифрования.
